## 1. Назначение

AiPayWorlds OS — локальное настольное приложение (desktop application) владельца/оператора проекта. Это не публичный пользовательский кошелёк и не публичный обозреватель на данном этапе.

Приложение должно запускаться и работать без интернета. Интернет является дополнительным каналом синхронизации (optional adapter), а не обязательной зависимостью.

## 2. Языки

Поддерживаются два режима:

- Русский — основной режим для Owner; интерфейс и учебные материалы по умолчанию на русском языке.
- English — полный английский режим.

В русском интерфейсе технические термины при необходимости показываются в скобках на английском. Для сложных элементов допускается подсказка (tooltip) с английским техническим термином.

Переключение языка не должно менять состояние проекта, настройки Земли, темы или локальные данные.

## 3. Центральный принцип UX

Земля (Earth Engine) является центральной сценой приложения, но не единственным содержанием.

Основные рабочие разделы располагаются в стабильной навигации. Дополнительные визуальные режимы, эффекты, темы и слои скрываются в компактном центральном контроллере возле Земли, чтобы не перегружать основной экран.

Не должно быть сухих экранов: каждый основной раздел получает соответствующее визуальное состояние центральной сцены.

## 5. Earth Engine

Обязательные режимы каркаса:

- Live Earth — расчёт положения Солнца по локальному времени/UTC.
- Day — принудительное дневное освещение.
- Night — принудительное ночное освещение.
- Home — точка Owner.
- Blockchain — визуализация узлов и связей.
- Payments — визуализация потоков платежей.
- Agents — визуализация AI-агентов.
- Security — визуализация событий безопасности.
- Infrastructure — визуализация серверов/узлов.
- Explorer — визуализация блоков и активности сети.
- Knowledge — визуализация связей знаний.
- Lab — визуализация экспериментов.
- Galaxy — будущий расширенный космический режим.

Слои включаются независимо через компактный контроллер.

## 6. Реальное время и офлайн-режим

Положение Солнца и граница день/ночь вычисляются локально и не требуют сети.

При наличии интернета приложение может получать внешние данные через строго определённые адаптеры: GitHub, RPC, погоду и другие разрешённые источники. При потере сети приложение не должно ломаться: последний валидный снимок данных сохраняется локально, а UI показывает состояние OFFLINE / LAST KNOWN.

Реальные онлайн-облака, погода и внешние карты не должны быть обязательными. Для автономной работы используется локальный набор текстур/данных (bundled asset pack), а онлайн-обновление является дополнительным режимом.

## 7. Технологический принцип F1

Целевая архитектура настольного приложения:

- Tauri 2 как desktop shell.
- Rust как привилегированный локальный backend (по мере необходимости).
- TypeScript как основной язык UI.
- Three.js или совместимый локально поставляемый 3D-движок для Earth Engine.
- Все frontend-зависимости фиксируются и поставляются локально.
- Никаких CDN, удалённых шрифтов, удалённых скриптов или обязательных внешних API для запуска.

Выбор Tauri 2 является архитектурной гипотезой F1, подлежащей проверке на локальной машине. Причина: лёгкий desktop shell, системный WebView, Rust backend и гранулярные capabilities/permissions.

## 8. Безопасность локального приложения

Frontend не получает произвольный доступ к файловой системе или shell.

Доступ к локальным ресурсам проходит через минимально необходимые capabilities/permissions. Удалённые источники не получают доступ к локальным командам приложения.

Секреты не должны попадать в frontend bundle, public repository или assets.

## 10. Анимации

Анимации должны быть семантическими (meaningful motion), а не декоративным шумом.

Примеры:

- новый блок → визуальное событие блока;
- Git-синхронизация → направленный импульс;
- платеж → поток между точками;
- агент → движение агента;
- security alert → локализованный сигнал риска;
- смена режима → плавный переход сцены.

Должен существовать глобальный Animation Budget с уровнями Off / Low / Medium / High / Cinematic и независимыми настройками качества.

## 11. Производительность

Цель — визуально насыщенное приложение, которое остаётся пригодным на слабом локальном железе.

Принципы:

- Level of Detail (LOD) для Земли.
- GPU-рендеринг там, где он даёт пользу.
- ленивое (lazy) создание тяжёлых сцен;
- ограничение частоты обновления для второстепенных элементов;
- отключение невидимых эффектов;
- локальный кэш;
- отсутствие постоянных фоновых сетевых запросов;
- измеряемые FPS, frame time и memory metrics.

## 12. Объём диска

Owner разрешает выделить до 40–50 GB под локальный asset/data budget приложения.

Это не означает, что приложение обязано занимать 40–50 GB. Диск используется только там, где это повышает качество: локальные Earth textures/LOD, дополнительные визуальные ресурсы, учебные материалы, документация, индексы и offline datasets.

Исходный код и тяжёлые бинарные assets должны быть разделены. Не следует помещать десятки гигабайт бинарных ресурсов в обычную Git-историю без отдельного обоснования.

## 13. Обучение владельца

Каждый крупный раздел должен иметь собственный учебный контур:

- цель;
- базовая книга;
- углублённая книга;
- практическая лаборатория;
- контрольный список;
- история прогресса;
- связь с реальным состоянием проекта.

Owner Book не является декоративным разделом: это встроенная система обучения оператора.

## 14. F1 exit criteria

F1 считается завершённым только после того, как:

- приложение запускается как desktop application;
- русский и английский режимы работают;
- навигационный каркас стабилен;
- тема и Animation Budget работают;
- Earth Engine имеет базовую сцену;
- офлайн-запуск не требует сети;
- нет обязательных CDN;
- базовая модель локального состояния определена;
- security boundary задокументирован;
- есть детерминированная проверка сборки/запуска;
- Owner Book имеет первый учебный модуль;
- дальнейшие модули можно добавлять без переписывания shell.

## 15. Что F1 не делает

F1 не утверждает:

- конкретный L1/L2;
- native token;
- mainnet;
- production wallet;
- real-money custody;
- публичный explorer;
- production RPC;
- production signing.

Эти решения остаются отдельными research/security/release gates.
